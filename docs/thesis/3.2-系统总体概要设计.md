## 3.2 系统总体概要设计

本节在3.1节需求分析的基础上，对钢材表面缺陷检测系统的整体架构进行概要设计，明确系统的层次划分、各层职责以及核心API接口规划。

### 3.2.1 系统整体架构设计

本系统围绕“用户提交检测任务、后端完成业务调度、模型执行缺陷识别、结果持久化并返回前端展示”这一主流程进行架构设计。整体上采用分层组织方式，自上而下划分为前端层、后端服务层、算法推理层、数据存储层和运行环境层，如图3-4所示。各层之间通过标准接口进行交互，前端不直接访问模型和数据库，后端负责统一接收请求并协调推理与存储，算法推理层只关注模型加载和检测计算，数据存储层则负责保存业务数据和文件资源。该设计能够将页面交互、业务逻辑、模型推理和数据管理分开维护，降低系统模块之间的耦合度。

（图3-4 缺陷检测系统技术栈架构图）

前端层主要承担用户交互与检测结果展示功能。系统使用 Vue3 构建单页面应用，通过 Vue Router 管理登录注册、缺陷检测、历史记录、统计仪表盘和模型管理等页面之间的跳转关系。检测页面负责接收用户上传的图像、模型选择和置信度阈值等参数，并通过 Axios 向后端发送 REST 请求；请求头中携带 JWT 信息，用于访问受保护接口。统计分析页面通过 ECharts 对检测数量、缺陷类别分布和历史趋势等信息进行可视化展示，使用户能够直观了解检测任务的整体情况。

后端服务层是系统业务逻辑的核心，由 FastAPI 应用和 Uvicorn 运行服务共同支撑，对外提供统一的 HTTP 接口。该层包含 Auth、Detections、Dashboard 和 Models 四类主要功能模块。Auth 模块负责用户注册、登录、JWT 签发与身份校验，并结合 bcrypt 对用户密码进行加密处理；Detections 模块负责接收单图或批量检测请求，校验上传文件和推理参数，并调用算法推理层完成缺陷检测；Dashboard 模块读取历史检测记录并进行统计聚合，为前端图表提供数据；Models 模块负责模型权重文件上传、模型列表维护和模型元数据管理。后端同时通过 SQLAlchemy 完成数据库访问，将接口请求、业务处理和数据读写组织在统一的服务层中。

算法推理层负责封装深度学习检测能力，是系统完成钢材表面缺陷识别的关键部分。该层以 PyTorch 和 Ultralytics YOLOv8 为基础，加载训练后的 CBAM 改进模型权重，提供单图推理和批量推理两类检测方式。为减少模型重复加载带来的时间开销，系统在后端维护 `_MODEL_CACHE` 模型实例缓存；当检测请求到达时，推理层优先复用已加载模型，只有在模型配置变化或缓存不存在时才重新加载权重文件。推理结束后，系统对输出结果进行后处理，生成缺陷类别、置信度、边界框坐标和标注图等信息；在需要提高检测稳定性时，也可启用 TTA 测试时增强策略，对多次预测结果进行融合。

数据存储层同时处理结构化数据和文件资源。结构化数据由 MySQL 数据库存储，主要包括 users、detection_records 和 uploaded_models 三类数据表，分别对应用户信息、检测记录和上传模型元数据。文件系统用于保存非结构化资源，包括用户上传的模型权重、批量检测输出目录以及检测后生成的标注结果图。后端服务层在完成检测后，会将类别、置信度、边界框、原图路径、结果图路径和所用模型等信息写入数据库，同时把标注图或批处理输出文件保存到文件系统中。数据库与文件系统之间通过路径字段建立关联，既避免将大文件直接写入数据库，也便于后续查询、展示和清理。

运行环境层为系统部署和推理执行提供基础支撑。系统运行在 Python 3.9 及以上环境中，可根据硬件条件选择 CPU 或 CUDA/GPU 加速推理。部署方式支持 Windows 和 Linux 本地环境，数据库服务、文件存储目录、后端接口服务与前端页面可以在同一主机上运行，也可以根据实际需要拆分部署。该层不直接参与业务处理，但会影响模型推理速度、文件读写效率和系统运行稳定性。

从图3-4所示的主调用链路看，用户在前端检测页面上传图像并选择模型、阈值等参数后，Axios 将检测请求发送至 FastAPI 后端；后端首先通过 JWT 完成身份校验，再由 Detections 模块查询模型信息、读取输入文件并调用算法推理层；推理层完成模型加载、缺陷检测和结果后处理后，将类别、置信度、边界框与标注图返回给后端；后端把结构化检测结果写入 MySQL，将标注图和批量输出保存到文件系统，最后以 JSON 格式将检测结果返回前端。通过这一流程，系统形成了从用户操作、模型推理、结果存储到可视化展示的完整闭环。

### 3.2.2 API接口规划

系统所有接口统一返回JSON格式数据。认证接口返回JWT Token，后续请求通过Authorization请求头携带Token进行身份验证。API文档通过框架自带的交互式文档自动生成。

主要接口规划汇总如表3-1所示。

**表3-1 系统API接口规划汇总**

| 接口路径 | 方法 | 功能 | 认证 |
|---------|------|------|------|
| /api/auth/register | POST | 用户注册 | 否 |
| /api/auth/login | POST | 用户登录 | 否 |
| /api/detections/predict | POST | 单张图片检测 | 是 |
| /api/detections/batch | POST | 批量图片检测 | 是 |
| /api/detections | GET | 历史记录查询（分页+筛选） | 是 |
| /api/detections/{id} | GET | 记录详情 | 是 |
| /api/detections/clear | DELETE | 清空历史记录 | 是 |
| /api/dashboard/stats | GET | 统计数据 | 是 |
| /api/models | GET | 模型列表查询 | 是 |
| /api/models/upload | POST | 模型文件上传 | 是 |
| /api/models/{id} | DELETE | 删除模型 | 是 |

上述接口覆盖了需求分析中定义的全部功能需求：认证模块支撑用户注册与登录（FR-001、FR-002）；检测模块支撑单张与批量检测（FR-003、FR-004）；历史记录查询与详情接口支撑检测记录管理（FR-005）；统计接口支撑数据可视化（FR-006）；模型管理接口支撑自定义模型上传与切换（FR-007）。各接口的详细设计与实现详见4.1节。
