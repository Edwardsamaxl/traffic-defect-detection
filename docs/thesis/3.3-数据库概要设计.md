## 3.3 数据库概要设计

本节基于系统需求分析，对持久层数据进行逻辑建模。设计遵循关系型数据库的规范化理论，以第三范式（3NF）为基准，兼顾查询性能与数据一致性，最终抽象出用户实体、检测记录实体与模型资源实体三类核心表结构。

### 3.3.1 设计原则与规范化策略

在数据库逻辑设计阶段，首要目标是消除数据冗余并避免更新异常。本系统严格遵循以下设计原则：

**（1）第三范式（3NF）合规性**

所有表结构均达到第三范式要求，即满足第二范式且不存在非主属性对主键的传递函数依赖。以检测记录表为例：用户相关的属性（如用户名）被剥离至用户表，模型相关的属性（如权重路径）被剥离至模型表，检测记录表仅保留对用户表和模型表的外键引用，从而避免了用户或模型信息变更时引发的级联更新异常。

**（2）字段原子性与类型精确性**

每个字段均为不可再分的原子值。例如，检测结果中的多目标边界框坐标、类别标签及置信度等复合信息，在业务层面属于同一逻辑实体，若以传统关系型字段拆分存储将产生大量稀疏列；因此系统采用 JSON 类型进行结构化存储，在保持逻辑完整性的同时兼顾了关系型 Schema 的整洁性。

**（3）索引策略与查询优化**

针对系统高频查询场景建立索引：用户表的 `username` 字段建立唯一索引以加速登录验证；检测记录表的 `user_id` 与 `created_at` 字段建立复合索引以优化"按用户分页查询历史记录"的性能瓶颈。索引的建立遵循"读取频繁、写入较少"的字段优先原则，避免过度索引导致的写入性能损耗。

### 3.3.2 数据表划分

根据第 3.1 节需求分析，系统在数据持久化层面需支撑三类核心业务：身份认证、检测任务追踪、模型资源管理。据此，数据库逻辑结构划分为以下三个表实体：

**（1）用户信息表（users）**

该表作为系统身份认证与权限管控的基石，存储注册账户的基础数据，包括用户标识、加密后的密码哈希及注册时间等核心属性。系统不存储明文密码，而是采用单向哈希处理，满足 Web 应用的安全基线要求。

**（2）检测记录表（detection_records）**

该表是系统的核心数据载体，用于持久化每一次检测任务的元数据与成果信息。其字段覆盖任务全生命周期：关联维度（所属用户、使用模型）、输入参数（置信度阈值、IoU 阈值）、输出结果（检出数量、结构化检测结果、标注图像）、图像元数据（原始尺寸）以及时间维度（任务完成时间）。

其中，检测结果采用 JSON 类型存储是本设计的一个关键决策。由于单次检测的目标数量不固定，传统关系模型需引入额外的"检测目标明细表"，这将导致每次查询需进行 JOIN 操作，增加 I/O 开销；而 JSON 字段可在单表内完成整次检测结果的读写，显著降低了查询延迟，同时通过应用程序层保证 JSON Schema 的一致性。

**（3）模型管理表（uploaded_models）**

该表负责维护系统可用模型的元数据目录，支撑模型库的高效检索与用户自定义模型的灵活接入。其字段包括模型展示名称、权重文件路径、是否为内置模型标记、上传者信息及注册时间。通过"是否为内置模型"标记与可空的上传者外键，实现了平台预设模型与用户上传模型的统一存储与差异化权限管理：内置模型由系统初始化导入，无明确属主；用户上传模型则严格绑定上传者身份。

### 3.3.3 表间关系与参照完整性

三张表通过外键约束建立关联，形成如图 3-5 所示的实体-关系（E-R）模型：

**（1）用户表与检测记录表：一对多（1:N）**

单个用户可发起多次检测任务，产生多条检测记录；每条检测记录严格隶属于单一用户。通过外键关联并设置级联约束：当用户账户注销时，其历史检测记录同步清理，避免产生孤立数据。

**（2）用户表与模型表：一对多（1:N）**

单个用户可上传并管理多个自定义模型实例，每个用户上传的模型均严格对应特定用户记录。平台预设的标准模型未指定所有权归属，其上传者字段置为 NULL，在关系代数中表现为可选参与（optional participation），体现了系统模型与用户模型的共存策略。

**（3）模型表与检测记录表：一对多（1:N）**

每条检测记录均唯一对应某一特定模型版本，而同一模型可被多次调用并生成多条检测日志。为实现基于模型的历史追溯功能，系统采用软引用与冗余备份相结合的策略：检测记录表除保存模型名称快照外，在模型被移除时，相关记录的模型引用字段自动更新为 NULL，但保留原始模型名称作为历史痕迹，确保检测日志的可读性与审计完整性。这一设计牺牲了极小的存储冗余，换取了数据生命周期解耦与历史可追溯性。

### 3.3.4 数据完整性约束

除上述外键关联外，系统还建立了以下完整性保障机制：

**（1）实体完整性**

三张表均以自增整数 `id` 作为主键，非空且唯一，确保每行记录的可标识性。

**（2）参照完整性**

所有外键字段均显式定义约束行为。用户表与检测记录表、用户表与模型表之间的外键均配置级联删除（ON DELETE CASCADE），保障主表记录移除时从表无孤立记录；模型表与检测记录表之间的关联则采用 ON DELETE SET NULL 策略，避免模型删除导致历史检测记录丢失。

**（3）用户定义完整性**

通过非空约束与唯一性约束，在数据库层面强制业务规则。例如，用户名唯一性约束防止重复注册；检测记录表的关键字段（文件名、置信度、IoU 等）非空约束确保每条记录均包含完整的任务上下文；模型路径唯一性约束防止同一权重文件被重复注册。

各表的具体字段定义、数据类型映射、索引配置及 ORM 实现详见第 5.3 节数据库详细设计。
