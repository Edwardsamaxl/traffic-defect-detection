## 5.5 统计分析模块实现

统计分析模块用于对用户已经完成的缺陷检测记录进行汇总展示。与缺陷检测模块直接返回单次检测结果不同，统计分析模块关注一段时间内的整体情况，包括累计检测次数、当日检测次数、近 7 日检测趋势以及不同缺陷类别的出现频次。该模块的数据来源为 `detection_records` 表，后端根据当前登录用户进行过滤和聚合，前端再将返回的数据渲染为指标卡和图表。图 5-X 展示了统计分析模块的核心类结构，图 5-X 展示了统计接口的数据处理流程，图 5-X 展示了前端仪表盘页面的实际效果。

从图 5-X 可以看出，统计分析模块主要围绕 `DashboardService`、`DetectionRecord` 和 `ChartData` 三部分展开。其中，`DashboardService` 是统计服务逻辑的抽象，在实际代码中由 `src/webapp/api/dashboard.py` 中的 `/api/dashboard/stats` 接口实现。图中的 `get_total_count(user_id)`、`get_today_count(user_id)`、`get_7day_trend(user_id)`、`get_class_distribution(user_id)` 和 `get_avg_daily(user_id)` 分别对应累计次数、今日次数、近 7 日趋势、类别分布和日均检测量等统计功能。实际代码没有单独定义这些方法，而是在 `get_stats()` 路由函数中按顺序完成这些聚合计算。

`DetectionRecord` 是统计模块的基础数据实体，对应 `src/webapp/models/detection_record.py` 中的 ORM 模型，也对应数据库中的 `detection_records` 表。该模型保存了检测记录编号、用户 ID、文件名、模型名称、置信度阈值、IoU 阈值、检测数量、检测结果 JSON、图片尺寸和创建时间等字段。统计模块主要使用其中的 `user_id`、`created_at`、`id` 和 `detections` 字段：`user_id` 用于保证只统计当前用户的数据，`created_at` 用于按日期筛选和分组，`id` 用于计数，`detections` 则保存每次检测得到的缺陷框列表，是类别分布统计的来源。

图中的 `ChartData` 可以理解为前端图表数据结构的抽象。后端接口实际返回的 JSON 中包含 `by_day` 和 `by_class` 两组数组：`by_day` 由日期和检测次数组成，用于绘制每日检测趋势折线图；`by_class` 由缺陷类别名称和出现次数组成，用于绘制缺陷类型分布图。这样的数据结构比较简单，前端不需要再进行复杂计算，只需提取标签和值即可交给 Chart.js 渲染。

统计分析模块的数据处理流程如图 5-X 所示。当前端仪表盘页面加载时，`DashboardView.js` 会通过统一的 Axios 客户端请求 `GET /api/dashboard/stats`。该请求会携带登录后保存的 Bearer Token，后端接口通过 `Depends(get_current_user)` 获取当前用户，并将 `DetectionRecord.user_id == current_user.id` 作为基础查询条件。这样即使数据库中保存了多个用户的检测记录，统计结果也只包含当前登录用户自己的数据。

在累计检测次数的计算中，后端使用 SQLAlchemy 的 `func.count(DetectionRecord.id)` 直接在数据库层完成计数。今日检测次数在此基础上增加日期条件，即 `func.date(DetectionRecord.created_at) == today`，用于统计当天产生的检测记录数量。这两类指标只需要简单的 COUNT 聚合，不需要读取完整记录，因此查询开销较小，也能直接反映用户的检测使用情况。

近 7 日检测趋势的计算采用“数据库分组统计 + 应用层补零”的方式完成。后端先计算最近 7 天的起始时间，再按 `func.date(DetectionRecord.created_at)` 对记录进行分组，统计每天的检测次数，并按日期排序。由于数据库分组查询只会返回有记录的日期，如果某一天没有检测记录，该日期不会出现在查询结果中。为保证折线图横轴连续，代码在 Python 端生成完整的 7 天日期序列，并将没有记录的日期补为 0。前端收到 `by_day` 后，将日期转换为 “月/日” 形式作为横轴标签，将 `count` 作为纵轴数值，最终绘制每日检测趋势折线图。

缺陷类别分布的统计需要解析 `detections` 字段。检测模块在写入记录时，会把每个检测框的类别编号、类别名称、置信度和边界框坐标保存为 JSON 数组。统计接口查询最近 7 天内当前用户的 `detections` 字段，逐条解析 JSON 内容，并根据每个检测框中的 `class_name` 进行累加。代码使用 `defaultdict(int)` 保存类别计数，遇到无法解析的 JSON 数据时会跳过该条记录，避免单条异常数据影响整个统计接口。类别计数完成后，后端按出现次数降序排序，并最多返回前 10 个类别，作为前端环形图的数据来源。

前端仪表盘页面的实现效果如图 5-X 所示。页面顶部为“数据统计”标题和“最近 7 天”的范围提示，中间第一行展示三张指标卡，分别为总检测次数、今日检测次数和日均检测次数。其中，总检测次数和今日检测次数来自后端接口返回的 `total_detections` 和 `detections_today`，日均检测次数由前端根据总检测次数除以 7 后取整得到。该处理方式使页面能够在不增加后端字段的情况下展示一个简要的平均水平指标。

页面下方为两块图表区域。左侧“每日检测趋势”使用 Chart.js 折线图展示最近 7 天每天的检测次数，折线图横轴为日期，纵轴为检测次数，并通过悬停提示显示具体日期和次数。右侧“缺陷类型分布”使用 Chart.js 环形图展示不同缺陷类别的占比，图例中列出类别名称，如 `inclusion`、`patches`、`rolled-in_scale`、`pitted_surface`、`scratches` 和 `crazing` 等。图 5-X 中的页面结果显示，系统已经累计保存 73 次检测记录，最近 7 天内部分日期检测量较高，类别分布则反映了各类钢材表面缺陷在检测结果中的出现情况。

统计分析模块没有单独维护统计表，而是直接基于检测记录表进行实时聚合。这种实现方式结构较简单，也能避免检测记录和统计结果之间出现不一致。对于当前系统的数据规模而言，基于 `user_id` 和 `created_at` 的查询能够满足仪表盘展示需求；同时，`DetectionRecord.created_at` 字段建立索引，有利于按时间范围查询。需要说明的是，缺陷类别分布目前在应用层解析 JSON 后统计，适合类别数量和近期记录数量不大的场景。如果后续系统检测记录规模继续扩大，可以考虑将检测框明细拆分为独立表，或在写入检测记录时同步维护类别统计表，以进一步提高聚合查询效率。

总体来看，统计分析模块的实现流程比较清晰：检测模块先把每次检测结果写入 `DetectionRecord`，仪表盘页面再请求统计接口，后端按当前用户和时间范围进行聚合，最后由前端渲染为指标卡、折线图和环形图。该模块把历史检测数据转化为更直观的统计信息，使用户能够快速了解自己的检测总量、近期检测变化以及缺陷类别分布情况，也为后续评估模型使用效果提供了基础数据。
